新增第四类故障：配置文件被写进了 UTF-8 BOM，宿主解析 JSON 时直接崩。

## 你会看到什么

- **新故障类：文件编码。** 报错长这样：`Unexpected token '﻿', "﻿{` —— 栈在 `readProfileManifest`，说明宿主在读 profile 的 `package.json` 时就崩了，插件一层都还没轮到。真凶是文件开头那 3 个字节（`EF BB BF`），Node 的 `JSON.parse` 不认。
- **新命令 `strip-bom`：** 扫 profile 根目录的 `*.json` / `*.yml` / `*.yaml`，把 BOM 去掉。只减 3 字节，内容不动。
- **`restore` 装回去时会自动去 BOM。** 这条比命令本身重要：坏掉的 `package.json` 可能已经被存进快照了，原样拷回来等于**忠实复现崩溃**。上一版就会这么干。
- **`status` 会直接报哪个文件带 BOM**，不用等崩溃。

## 为什么会出这种事

用 **PowerShell 5.1** 写这几个文件就会带 BOM —— `Set-Content -Encoding UTF8`、`Out-File`、`ConvertTo-Json | Set-Content` 在 5.1 里都写 BOM。判断痕迹：如果你的 `package.json` 里是 `"name":  "..."`（冒号后两个空格），那是 PowerShell `ConvertTo-Json` 的产出。

改这些文件请用 `pwsh`，或显式 `-Encoding utf8NoBOM`。

## 顺带修掉的一个静默失败

上一版去 BOM 的做法是"先拷过去，再就地改"。应用在运行时那个文件是锁着的，这一步会**失败但不报错**——于是命令打印成功，BOM 还在，下次启动照样崩。现在改成"读源文件 → 去 BOM → 原子写目标"，没有那一步了。

## 验证

- 假 profile：造两个带 BOM 的文件 → `strip-bom` 去掉后 `JSON.parse` 通过、字节数正好减 3。
- 真快照含 BOM 时 `restore`：装完后 `package.json` 无 BOM、8 个依赖可解析、`node_modules` 113 个包。
- `diagnose` 对这份日志判出"丁类"并指出该跑 `strip-bom`。

## 安装

```powershell
pwsh -NoProfile -File "$env:USERPROFILE\.dsh\rescue\dsh-rescue.ps1" install
```
